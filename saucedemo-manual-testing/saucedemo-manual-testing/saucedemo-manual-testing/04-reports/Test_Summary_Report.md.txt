## 7. Retest and Regression
**Approach:** The site's code cannot be modified, so `standard_user` was used as the simulated "fixed build" and each defect's steps were re-run. This is a simulated fix verification, not a real developer fix.

| Item | Result |
|---|---|
| Defects retested | 6 |
| Closed (Pass) | 4 (TC37, TC38, TC39, TC40) |
| Reopened (Fail) | 2 (TC26, TC27) |
| Regression cases run | 6 of 40 (15%): 4 passed, 2 failed |

The empty-cart defects were not user-specific, so they were reproduced as standard_user and remain open.

## 8. Risks and Known Issues
- Two Major defects (empty-cart checkout and order completion) remain open.
- Regression covered only 6 of 40 cases, so unrelated regressions may be undetected.
- Requirements were reverse-engineered because the site has no spec, so some expected results are assumptions (for example REQ-17).
- `problem_user` and `error_user` bugs are built into the demo site, so the "fix" was simulated.
- The public demo site may change over time.

## 9. Lessons Learned and Recommendations
- Running the same flows with different user types found more defects than standard_user alone.
- Run the full regression suite after every fix, not just the failed cases.
- Fix the empty-cart validation first, because it allows invalid orders.
- Automate the regression suite in a later phase.
